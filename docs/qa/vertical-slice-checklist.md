## Fixed contracts and architecture

- WASD is the only movement keyboard composite; Left Shift Hold is Sprint, Space is Dash, mouse position Aim and left mouse click Attack. UI navigation retains its own action map. No core key was repurposed. PlayerInputReader clones the actions and owns gameplay reads; no scattered Keyboard.current/Mouse.current in player logic.
- PlayerMotor2D is the sole player Rigidbody2D velocity/position writer. Dash takes priority over movement/sprint; sprint never multiplies Dash speed. MovementRules clamps diagonal magnitude while preserving analog magnitude. Dash timing/distance/cooldown are PlayerStats settings; no stamina/toggle/I-frame subsystem was added.
- Orthographic camera, XY transforms, Rigidbody2D, Collider2D, SpriteRenderer and zero gravity are tested and used. Sprite bodies remain visible with existing URP. Native standalone screenshot inspection confirmed rendered sprites and room walls.
- Core assembly has `noEngineReferences: true`. Unity lifetime/input/collision adapters use separate components. Bootstrap owns the session; no global Singleton or broad event bus is required. Runtime HP, inventory, evolution, combo and Momentum live in per-run objects/components, not ScriptableObject assets.
- The two combo definitions consume accepted combat actions. Momentum and evolution additionally require actual hit qualification. Empty input/Dash spam does not generate growth. Definition priority is longest sequence, priority, then stable ID. Completion consumes history; weapon switch/death/new run clears state.
- Data assets configure weapons, enemies, player stats, items, combo definitions, evolution threshold/wave, Rebirth upgrades/multipliers and Threat reward. New fundamentally different behaviors may require code as PLAN allows; no unnecessary no-code editor or DI framework exists.
- Safe/Shortcut/Boss are genuine playable rooms. Reward selection blocks departure until consumed; completion/settlement is once per room/run. RunResult preserves base and adjusted Gold, retention and Bank. Next run resets combat state while Profile persists.
- Save schemaVersion is the envelope version; Profile stores Count, permanent multiplier, points, upgrade IDs, unlock IDs, settings, Bank Gold, clears and settlement ID. Real storage uses persistentDataPath by default; opt-in development QA uses a validated child directory. No mid-run resume is stated in UI and README.
- Unlock IDs and purchased upgrades survive Rebirth. Initial cost 100 and multiplier sequence 1/2/2.7/3.4 are data, not fixed design requirements. Two permanent upgrades provide HP +20 and combo window +0.25s; Threat 1 uses real three-arrow attacks rather than just HP/damage scaling.
- Original pixel art Explorer, Dagger/Sword/Greatsword/Bow, Slime/Goblin/Boar and effects are bound in prefabs/data. Bow grip mirroring, hands/draw/recoil and melee swing have dedicated regression tests. Final commercial graphics and animation sets are outside this Slice.

## Deliverables and scope

- Gameplay loop: Main Menu → Hub → weapon selection → Dungeon → combat/reward → Safe or Dangerous route → Boss → Victory/Death → Result → Hub → meta/Rebirth → increased Threat → next run. Standalone smoke proves Safe/Victory/Rebirth; full PlayMode proves Shortcut, Death and evolution branches.
- Automated coverage includes damage, movement, Dash cooldown, Momentum, combos, weapon stats/evolution, graph, rewards, Rebirth/Threat and serialization. Final test XMLs provide individual case names/results. Dedicated relaunch tests execute in separate processes rather than being counted as run when skipped in the ordinary suite.
- Milestone commits exist in order from `a859db1` (M0) through `c245e01` (M12); M13 code/docs are recorded by the completion commit containing this audit. QA history preserves failure/fix/retest evidence, rather than deleting failed tests.
- README records Editor/standalone launch, controls, reproducible build/test commands, save location and limitations. BuildScript explicitly includes only MainMenu/Hub/Dungeon; EditorBuildSettings retains test scenes for test execution. Distribution must include the entire Build folder, not only the exe.
- One theme, three archetypes + one Elite modifier, one Boss/two patterns, four authorized weapons, three run items, two combos, one evolution, two upgrades and Threat 0/1 behavior. No multiplayer/server/account/Steam/cloud/crafting/achievement/extra themes or production migration/DI infrastructure was added.

## Explicit outstanding human checks

`MANUAL_PLAYTEST_REQUIRED`: movement/sprint/Dash feel; aiming and attack feedback/readability; ordinary-player combo/evolution difficulty; room/shortcut danger readability and balance; Boss telegraph/counterattack difficulty; first Rebirth pacing and perceived permanent growth; final art approval. Automated and agent-driven UI checks do not substitute for these. Under the user's explicit manual-test limitation, these do not prevent completion of otherwise verified implementation.

Exact minimum specification, release build optimization, broad CPU/GPU profiling, controller shipping support, animation polish and future real-schema migration are deferred by PLAN, not missing Slice requirements.
